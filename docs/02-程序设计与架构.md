# lifeOS · 程序设计与架构（多端 + 云存储版）

> 版本：v3.8 草案　|　对应需求见《01-详细设计.md》；v3.3 修订习惯频率模型与时区约定；v3.4 习惯三态打卡与提醒；v3.5 补签卡与 emoji 选择器；v3.6 计划进度自动汇总；v3.7 计划树形视图；v3.8 计划删除级联
> 范围：Windows 桌面端 + 网页端 + Android 手机端（不含 iOS）；数据库部署在自有云服务器（PostgreSQL，备选 MySQL）；后期预留向量化能力。
> **开发策略：Mock 先行——第一阶段不接数据库，全量功能用 Mock 数据跑通验收；预留 Repository 数据接口，后期统一接入真实数据库。**

---

## 1. 核心架构决策（一图看懂）

| 决策 | 选型 | 一句话理由 |
|------|------|-----------|
| 三端复用 | **一套 React 核心 + 三个外壳** | 业务逻辑 100% 一致，避免三套代码重复维护 |
| Windows 桌面 | **Tauri 2**（备选 Electron） | 体积小（~10MB vs ~100MB）、内存低、Rust 安全 |
| Android 手机 | **Tauri 2 移动端**（备选 Capacitor） | 与桌面同一工具链；Capacitor 为成熟备胎 |
| Web | Vite + PWA | 免安装即用，可「添加到主屏」 |
| **数据访问** | **Repository 抽象 + Mock 先行** | 第一阶段不接库、用 Mock 跑通全量功能；接口即「数据库接口」，后期只换实现 |
| 后端 | Node.js + Fastify + Prisma（接入阶段启用） | 轻量、TS 全栈统一 |
| 数据库 | **PostgreSQL + pgvector**（备选 MySQL） | 后期向量化需求，pgvector 是决定性因素 |
| 缓存/队列 | Redis（后期，向量化/通知用） | 异步任务 |
| 文件存储 | 服务器磁盘卷（可迁 S3/MinIO） | 图片量小，先简单后平滑 |
| 部署 | 云服务器 + Docker Compose + Caddy（接入阶段） | 一键自托管、自动 HTTPS |

## 2. 多端架构

### 2.1 分层思想：一套核心，三个外壳

```
┌───────────────────────────────────────────────────────────┐
│                     共享核心（apps/web）                    │
│   React + TS + AntD：全部页面/业务逻辑                       │
│   平台无关，只依赖两个抽象接口：                              │
│   ① PlatformCapabilities（平台能力）  ② DataSource（数据）   │
└───────────────┬───────────────────────────┬───────────────┘
                │                           │
   ┌────────────┼───────────────┐   ┌───────▼──────────────────┐
   ▼            ▼               ▼   ▼  DataSource 接口（见 §3）   │
┌────────┐ ┌──────────────┐ ┌─────────────────┐  Mock 实现 / Remote 实现
│  Web   │ │ 桌面外壳      │ │ 手机外壳         │
│ (PWA)  │ │ Tauri 2      │ │ Tauri 2/Capacitor│
└────────┘ │ (Windows)    │ │ (Android)        │
           └──────────────┘ └─────────────────┘
```

- **共享核心**只做「界面 + 业务」，通过 `PlatformCapabilities` 与 `DataSource` 两个接口调用外部能力，不直接碰任何原生 API、也不直接碰存储。
- 每端提供一个「外壳」，只负责启动、系统集成与两个接口的具体实现。
- 加新平台 = 新写一个外壳；换数据库 = 换一个 `DataSource` 实现。核心零改动。

### 2.2 平台能力适配层（关键抽象）

```ts

```

| 能力 | Web（PWA） | Windows 桌面（Tauri） | Android（Tauri/Capacitor） |
|------|-----------|----------------------|---------------------------|
| 本地通知 | Notification API | 原生通知/托盘 | 原生通知 |
| 图片 | 文件选择器 | 系统对话框 | 相机/相册 |
| 分享 | Web Share API | 系统分享 | 系统分享 / 接收分享进日常 |
| 备份导出 | 浏览器下载 | 另存为对话框 | 保存到下载目录 |
| 生物解锁 | — | Windows Hello（可选） | 指纹/面容（可选） |
| 桌面特有 | — | 托盘、全局快捷键、开机自启 | — |

### 2.3 三端体验差异

| | 网页端 | Windows 桌面端 | Android 手机端 |
|--|--------|---------------|---------------|
| 安装 | 免安装 / PWA | 安装包（MSI/NSIS） | APK |
| 定位 | 零门槛访问 | 常驻后台、托盘提醒、快捷记账 | 随身记录、拍照、随时打卡翻书 |
| 特色 | 任意设备浏览器打开 | 开机自启 + 提醒不丢 | 拍照记日常、系统分享入口 |

## 3. 数据访问抽象层（Mock 先行，核心设计）

### 3.1 核心理念

> **第一阶段不接数据库。** 先把五大板块 + 纸质书架 + 主面板的全部功能在 Mock 数据上开发、跑通、验收；「数据库接口」= 本节定义的 `DataSource` 契约。等全量功能没问题后，新增一个 `RemoteDataSource` 实现（走 HTTP → Fastify → PostgreSQL），通过一行配置切换，UI 与业务逻辑零改动。

### 3.2 契约定义（= 预留的「数据库接口」）

接口放在 `packages/shared`，从第一天起就是最终形态，Mock 与 Remote 都实现同一份：

```ts
// —— 按领域拆分的 Repository ——
interface HabitRepository {
  list(): Promise<Habit[]>;
  create(input: HabitInput): Promise<Habit>;
  update(id: string, patch: Partial<HabitInput>): Promise<Habit>;
  remove(id: string): Promise<void>;
  checkIn(habitId: string, date: string): Promise<HabitCheckIn>;
  uncheck(habitId: string, date: string): Promise<void>;
  listCheckIns(habitId: string, from: string, to: string): Promise<HabitCheckIn[]>;
}
interface PlanRepository     { list(filter): Promise<Plan[]>; create/update/remove/reorder ... }
                             // create/update/remove 后自动沿祖先链重算父计划进度（见 Plan 模型注释）；
                             // 父计划 update 中的 progress/status 会被子计划汇总结果覆盖
                             // 树形视图：PlansPage 以当前周期筛选结果为根、全量 plans 组装父子树（UI 层关注点，
                             // 数据层无需改动）；排序改为同级兄弟两两交换 order（经 update 实现）
                             // remove：递归级联删除全部后代计划，避免孤儿节点
interface BookRepository {
  list(filter?: BookFilter): Promise<Book[]>;
  get(id: string): Promise<Book | null>;
  create(input: BookInput): Promise<Book>;
  update(id: string, patch: Partial<BookInput>): Promise<Book>;
  remove(id: string): Promise<void>;
  logProgress(bookId: string, input: ReadingLogInput): Promise<ReadingLog>;
  listLogs(bookId?: string): Promise<ReadingLog[]>;
  createNote(bookId: string, input: BookNoteInput): Promise<BookNote>;
  listNotes(bookId?: string): Promise<BookNote[]>;
  removeNote(id: string): Promise<void>;
}
interface FinanceRepository  { /* categories / accounts / transactions / budgets */ }
interface AssetRepository    { /* 实物 + 订阅 CRUD */ }
interface MomentRepository   { /* 时间线 + 图片 */ }
interface SettingsRepository { get(): Promise<Settings>; update(patch): Promise<Settings> }
interface StatsRepository    {
  dashboard(): Promise<DashboardStats>;
  finance(period?: string): Promise<FinanceStats>;
  reading(year?: number): Promise<ReadingStats>;
}

// —— 统一数据源入口 ——
interface DataSource {
  habits: HabitRepository;
  plans: PlanRepository;
  books: BookRepository;
  finance: FinanceRepository;
  assets: AssetRepository;
  moments: MomentRepository;
  settings: SettingsRepository;
  stats: StatsRepository;
  backup: BackupRepository;
}
```

### 3.3 两个实现

```ts
// 实现一：Mock（第一阶段使用）
class MockDataSource implements DataSource {
  // · 数据存 localStorage（关浏览器不丢，体验接近真实）
  // · 内置种子数据 + 「一键生成演示数据」
  // · 模拟 200~400ms 网络延迟，让 loading/骨架屏状态真实
  // · 可选模拟错误，验证错误提示 UI
}

// 实现二：Remote（接入阶段启用）
class RemoteDataSource implements DataSource {
  // · 调 /api REST（见 §8），与契约一一对应
  // · 走 TanStack Query 做缓存/失效/乐观更新
}
```

### 3.4 切换机制

```ts
// apps/web/src/data/index.ts —— 一行配置切换数据源
export const dataSource: DataSource =
  import.meta.env.VITE_DATA_SOURCE === 'remote'
    ? new RemoteDataSource(apiClient)
    : new MockDataSource();
```

- 开发/验收阶段：`VITE_DATA_SOURCE=mock`（默认）。
- 接入阶段：`VITE_DATA_SOURCE=remote`，指向真实 API。
- 全程业务代码只 `import { dataSource }`，**不感知数据来自哪里**。

### 3.5 契约先行：Mock 与后端对齐

- 实体类型（§6）+ Repository 接口（§3.2）+ API 的 Zod schema（§8）**全部先在 `packages/shared` 定死**。
- Mock 阶段前端照契约开发；接入阶段后端**严格按同一契约实现 API**，无需重新对接口，避免返工。
- 数据模型（§6）第一天就是最终形态——后期只是把「localStorage 里的同一份 JSON」搬进 PostgreSQL。

## 6. 数据模型（契约，Mock 阶段即定稿）

### 6.1 通用约定
- 主键 `id`：`cuid2`；所有业务实体带 `userId`（接入阶段多用户用，Mock 阶段为固定单用户）、`createdAt`、`updatedAt`。
- 日期 `YYYY-MM-DD`；时间戳 ISO；金额一律「分」（整数）。
- 列表型字段（tags、links、byCategory）在接入阶段用 PostgreSQL `JSONB`；Mock 阶段为同结构的 JS 对象。

### 6.2 实体定义（TS 契约；接入阶段映射为 Prisma 模型）

```prisma
model User { id, email, passwordHash, name?, avatarUrl?, createdAt, updatedAt }
model RefreshToken { id, userId, tokenHash, expiresAt, revokedAt? }

// —— 自律 ——
model Habit {        // name, icon, color, frequency('daily'|'weekly'|'custom'),
                     // timesPerPeriod(daily: 每天 N 次；weekly: 每周 N 次弹性目标), weekdays?(custom: 调度星期几, 1–7),
                     // reminderTime?, allowBackfillDays, archived
  checkIns HabitCheckIn[] }
model HabitCheckIn { // habitId, date('YYYY-MM-DD'), count(当日完成次数, 默认 1, 上限 timesPerPeriod),
                     // state('done'|'skip', 默认 'done'；skip=休息日，不清 streak 不计未完成), note?
  @@unique([habitId, date]) }   // 同日重复 checkIn 递增 count 而非新增记录；uncheck 递减 count 至 0 则删记录

// —— 计划 ——
model Plan {         // title, description?, level('year'|'month'|'week'|'day'),
                     // period, parentId?, status, progress(0-100), priority, order }
                     // 进度口径：叶子计划手动维护；父计划由未取消直接子计划进度平均自动汇总，
                     // 状态随进度派生(100→completed, >0→in_progress, 0→not_started)；
                     // 勾选父计划级联完成全部未取消后代，取消勾选仅回退已完成后代

// —— 纸质阅读 ——
model Book {         // title, author?, totalPages, currentPage, status('queue'|'reading'|'finished'|'abandoned'),
                     // category?, coverUrl?, coverTheme?, rating?, review?, startDate?, finishDate?
  logs  ReadingLog[]
  notes BookNote[] }
model ReadingLog {   // bookId, page, pagesRead, note?, date('YYYY-MM-DD') }
model BookNote {     // bookId, pageNumber?, quote, thoughts?, tags Json, embedding? }

// —— 记账 ——
model Category {     // name, icon, color, type('expense'|'income'), parentId?, isSystem }
model Account {      // name, icon, initialBalance(分), archived }
model Transaction {  // type, amount(分), categoryId, accountId, date, note?, tags Json, embedding? }
model Budget {       // period('YYYY-MM'), total(分), byCategory Json }

// —— 资产 ——
model Asset {        // kind('physical'|'subscription'), name, icon, category
                     // 实物: purchaseDate?, purchasePrice?, brand?, model?, serialNo?, warrantyUntil?, estimatedValue?, status
                     // 订阅: price?, billingCycle?, startDate?, expireDate?, autoRenew?, accountNote? }

// —— 日常 ——
model Moment {       // content, imageUrls String[], mood?, weather?, location?, tags Json, links Json, embedding? }

// —— 设置 ——
model Settings { userId String @id; currency; theme; weekStartsOn; annualReadingTarget?;
                 makeupCardBalance(补签卡余额, 每月发放 2 张, 当月未用完不累积); makeupCardMonth(已发放月份 'YYYY-MM') }
```

> `embedding` 列为后期向量化预留（§7），通过增量 migration 加入。

## 7. 数据库选型与向量化（接入阶段启用）

### 7.1 为什么选 PostgreSQL 而非 MySQL

| 维度 | PostgreSQL | MySQL |
|------|-----------|-------|
| **向量检索** | ✅ `pgvector` 原生扩展，HNSW/IVFFlat 索引 | ❌ 社区版无一等向量能力 |
| 半结构化数据 | ✅ JSONB（索引、查询、更新） | 🟡 JSON 功能较弱 |
| 聚合/统计 | ✅ 窗口函数、CTE、物化视图强 | 🟡 够用但弱一些 |
| 生态 | Prisma 一等支持 | 同等支持 |

**结论**：你提到「后期可能向量化」，这一条基本锁定了 PostgreSQL。个人数据量（万级记录）用 `pgvector` 单实例绰绰有余，不需要独立向量库（Milvus/Qdrant）。部署镜像：`pgvector/pgvector:pg16`。

### 7.2 向量化三步路线（后期，非 MVP）

```
R1 建模：moment / book_note / transaction 等表加 embedding vector(N) 列（migration，无感）
R2 管线：数据变更 → Redis 队列 → embedding 服务 → 写回 pgvector（自托管 bge-m3 或调 API）
R3 应用：语义搜索 /api/search · AI 问答(RAG) · 智能记账分类 · 月度自动复盘
```

## 9. 认证、同步与离线策略

- **认证（接入阶段）**：bcrypt 密码哈希；access token（15 分钟，内存）+ refresh token（30 天，httpOnly cookie，轮换 + 重放检测）。Mock 阶段为固定单用户，无认证。
- **在线优先（接入阶段）**：读写走 API；TanStack Query 统一缓存/失效，切回前台自动刷新。
- **乐观更新**：打卡、记一笔、勾计划、翻书记录先改 UI，失败回滚提示。
- **冲突**：多端「最后写入获胜」，`updatedAt` 比对，过期写入 409 → 拉最新重试。
